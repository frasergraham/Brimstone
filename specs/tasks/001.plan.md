## Approach

### Dice math

**Advantage N**: roll `1 + N` d6, take the **single highest**.
**Disadvantage N**: roll `1 + N` d6, take the **single lowest**.
**Neutral**: roll 1 d6 (unchanged).

A side's net advantage = (advantage sources) − (disadvantage sources). If the
net is positive, that side gets advantage dice equal to the net; if negative,
disadvantage dice equal to |net|; if zero, a plain d6. This is computed
independently for attacker and defender so the interaction question
("what if both apply?") is answered at the *source-counting* level, not by
cancelling after rolling.

Expected value reference (single d6 → best-of-K / worst-of-K):

| K   | best-of-K E[·] | worst-of-K E[·] |
|-----|---------------:|----------------:|
| 1   | 3.50           | 3.50            |
| 2   | 4.47           | 2.53            |
| 3   | 4.96           | 2.04            |
| 4   | 5.24           | 1.76            |

Compare to the current flat-bonus world: phase = +2, staff = +2, each gang-up
ally = +1 d3 (E ≈ 2.0). One die of advantage adds ≈ +1.0 to the expected roll;
two dice add ≈ +1.5. **Advantage is weaker than today's flat +2 phase bonus
but stronger than a single gang-up d3 in expectation, and it compresses
variance at the high end** (capped at 6). Expect win rates to shift —
prediction: night-witch dominance decreases, outnumbered heroes fare slightly
better because disadvantage-2 on the witch is a larger relative swing than a
flat −2.

### Mapping current modifiers → advantage/disadvantage

| Source | Current | Proposed |
|---|---|---|
| Phase (day → hero, night → witch) | +2 ATK to favored side | +1 advantage die on that side's attack roll AND +1 disadvantage die on opposing side's attack roll? → **choose one: advantage-only**, simpler and symmetric |
| Silver weapon (+1 ATK next battle) | flat `attackBonus = 1` | +1 advantage die on attack; consume after the roll as today |
| Staff vs undead/minions/golems | flat +2 ATK | +1 advantage die on attack |
| Gang-up (each attacker ally adjacent to target) | +1 d3 per ally, capped at 3 d3s | +1 advantage die per ally, capped at 3 |
| Defender allies (each adj to target) | +1 d3 per ally, capped at 3 | +1 advantage die on defense per ally, capped at 3 |
| Fatigue | flat −1/−2 defense | **keep flat** (see Fortification section — same rationale) |

### Ally pool sizing

Cap total advantage/disadvantage dice on each side at **3**. Same cap as
today's d3 cap on gang-up. Sources stack before the cap: e.g. witch attacking
at night with 2 gang-up minions = advantage-3 (phase 1 + gang 2, capped). Both
sides compute independently; the other side's disadvantage does not subtract
from this side's advantage. One exception: if we choose the symmetric
phase-bonus framing ("day gives hero advantage AND witch disadvantage"), the
disadvantage-die budget is its own capped pool.

**Decision:** start with **asymmetric phase** (phase grants advantage only to
the favored side, not disadvantage to the other). Simpler, smaller balance
delta, easier to reason about in tests. Revisit if sim shows phase no longer
matters.

### Interaction when both apply

Advantage and disadvantage are *separate source counts per side*. If a side
has both (e.g. witch has phase advantage but is also attacking uphill with
some future disadvantage source), they **net out numerically first** (A − D),
then the side rolls advantage/disadvantage/neutral based on the net sign.
This is the 5e convention and it's the least surprising for play.

## Fortification decision

**Decision: keep fortification as a flat defense bonus** (not converted to
advantage dice).

**Rationale:**

1. Fortify is a *player-chosen investment* (spent actions, tile-bound) with a
   tunable integer level (1/2/3). Collapsing that to "0/1/2/3 dice of
   advantage" would either lose granularity (fort 2 and fort 3 feel the same
   in expectation) or push the total advantage budget past the cap when
   stacked with ally defense dice.
2. Flat defense bonuses on a *location* preserve the "holding ground" feel —
   a fortified defender with no allies should still feel solidly harder to
   hit, not just slightly luckier.
3. Balance containment: fortify currently contributes a small, predictable
   share of witch-kill-hero failure cases. Converting it pushes more variance
   into defender rolls exactly when defender allies are also advantaging —
   unnecessary compounding.
4. Fatigue (the defender's counterbalance) is flat; keeping fortification
   flat preserves their symmetry.

We will note the decision in the PR body as required by the acceptance
criteria.

## Risks

- **Balance shift larger than 12%.** Plausible: converting phase +2 → 1
  advantage die is a nerf to night-witch; converting gang-up d3 → 1 advantage
  die is roughly neutral on the first ally but a nerf at 3 allies. Mitigation:
  full sim sweep per test strategy; if witch win rate drops below 38%, either
  keep phase at +2 (leave it flat) or give the favored side +2 advantage dice
  instead of +1. Document the final dial in CLAUDE.md.
- **AI estimator drift.** The advantage/disadvantage estimator requires
  computing E[best-of-K] / E[worst-of-K] instead of a simple `+ gangUpDice *
  2` term. If we get the approximation wrong, the AI will systematically
  mis-pick battles. Mitigation: use a small lookup table for K∈{0,1,2,3}
  rather than a closed-form, and add the parity test above.
- **Hidden flat-bonus call sites.** `executeBattle` at `src/actions.js:756`
  and the guard counter at `src/actions.js:1249` both pass flat
  `atkFortAtkBonus` / `fortBonus` / `phaseBonus` / `fatiguePenalty`. Signature
  change will touch both. `scripts/combat-sim.js` calls `resolveCombat`
  directly at lines 43/80/97. `tests/tutorial.test.js` calls it at lines
  177/189/195. All must be updated in lockstep or the suite breaks.
- **Allowlist mismatch.** Task lists `src/ai.js` but real combat estimation
  lives in `src/ai-engine.js` + `src/hero-ai-engine.js`. Also the signature
  change reaches `src/actions.js`. Confirm expanded allowlist before
  implementation PR.
- **Tutorial forced-dice queue.** `Entity.resolveCombat` consumes an RNG
  queue used by the tutorial for scripted rolls. Going from 2 dice per combat
  to up to 8 (1 + 3 advantage on each side) changes how many queue entries
  each combat consumes. Tutorial scripts must be audited — likely need
  re-authoring. Flag before implementation; possibly scope-extend to
  `tutorial.js`.
- **Online/offline parity.** Combat runs through shared `entities.js` so no
  duplication risk, but `server/state-sync.js` should be sanity-checked — no
  new state fields are expected, just confirming.
