# 002 — Agility stat — Implementation Plan

## Files to change (within allowlist)
- `src/entities.js` — add Agility to `Entity` construction and to survivor roster defaults; export a per-type defaults map.
- `server/resolver.js` — reshape step-draining in both `resolvePlansMP()` and `resolvePlans()` so within a single step, queued entity actions execute in Agility-descending order with deterministic tie-breaks.
- `server/state-sync.js` — serialize and deserialize `agility` on every entity.
- `tests/resolver.test.js` — resolution-ordering tests with mixed-agility units (ideally extend existing file; add new if missing).
- `tests/state-sync.test.js` — Agility persists across serialize→deserialize round-trip.

## Approach

### Entity factories — where Agility lives
Add a new `BASE_AGILITY` table next to `BASE_STATS` in `src/entities.js`, keyed by `EntityType`. Proposed per-type defaults (1–10 scale):

| Type        | Agility | Rationale                                                     |
|-------------|--------:|---------------------------------------------------------------|
| HERO        | 6       | Protagonist acts before most foes; leaves headroom for gear.  |
| WITCH       | 5       | Caster, deliberate; below hero but above her rank-and-file.   |
| SURVIVOR    | 4       | Default for allies; individual roster entries may override.   |
| ZOMBIE      | 2       | Shambling — slowest of the witch's swarm.                     |
| MINION      | 6       | Quick skirmisher; matches hero so minions can intercept.      |
| WOOD_GOLEM  | 3       | Heavy construct.                                              |
| IRON_GOLEM  | 2       | Heaviest construct — last to act.                             |

These are a first pass; Step 6 (balance check) may nudge individual values. The numbers are kept intentionally bunched near the middle of the 1–10 range so future tuning (survivor abilities like SCOUT/TRAPPER, weapon effects) can span the ends without re-baselining everything.

Set `this.agility` in the `Entity` constructor from `BASE_AGILITY[type]`. In `createSurvivor()`, after the base-stats apply step, read an optional `agility` field from the roster entry (if present) and overwrite — this lets flavorful characters (e.g. Ezra Boone the Trapper, Silas Holt the Farmhand) be quick without plumbing abilities. The initial survivor-roster edit is out of scope; we only add the override plumbing. Everyone uses the base 4 at first.

### Sort insertion — `resolvePlansMP`
Currently each step iterates players in a fixed order, and within a player iterates `unitQueues` in Map insertion order. To sort by Agility without breaking the paired-step model, restructure the inner loop of the main `while (true)` as follows:

1. Build a flat list of `drainCandidates` for this step: for each player and each `(entityId, queue)` in `player.unitQueues` with `queue.length > 0`, push `{ player, entityId, queue }`.
2. Look up each candidate's current actor via `state.entities.find(e => e.id === entityId && e.alive)`. If missing/dead, keep the candidate with `agility = -Infinity` — the existing skip logic inside `drainOneStep` will clear its queue entry naturally.
3. Sort `drainCandidates`:
   - Primary: `actor.agility` **descending** (higher acts first).
   - Tie-break: numeric entity id ascending — parse the digits after the leading `e` (e.g. `e10` → 10) so `e2` comes before `e10`. Use a helper `_entityIdNum(id)` local to resolver.js.
4. Iterate the sorted list, calling `drainOneStep(state, queue, player.budget)` for each, and group the returned events back under their owning player for the step record.

The *step* is still one logical slot per entity: each candidate drains at most one action-cost (plus any free skips / guard strikes, as before). Per-player budgets remain per-player — sort only affects ordering, not accounting. The outer `while (true)` termination condition (`anyAction === false`) is unchanged.

Per-player event grouping: build a `Map<playerId, SubEvent[]>` as events come back, then emit one `{ playerId, faction, events }` entry per player that produced events this step, preserving the existing `StepRecord.playerEvents` shape so downstream consumers (animation layer, client mirror) are unaffected.

### Sort insertion — legacy `resolvePlans`
Apply the same restructure. Flatten hero + witch unit queues into one candidate list, sort by Agility/id, drain each, and split the resulting events back into `heroEvents` / `witchEvents` arrays by looking at each queue's budget-faction (or by remembering it alongside the candidate). Existing output shape (`{ stepIndex, heroEvents, witchEvents, entitySnapshot }`) is preserved.

### Determinism
- Sorting uses only `actor.agility` and numeric entity id; both are serialized fields that both orchestration paths (offline in `src/main.js`, online in `server/lobby.js`) share via `state.entities`. No `Math.random()` enters the sort.
- `Array.prototype.sort` is not guaranteed stable in all JS engines before ES2019, but modern Node/browsers are stable. The explicit id tie-break makes stability irrelevant — no two candidates can compare equal.
- Agility is read **once per step** before draining, so a mid-step death/scatter does not reorder already-selected candidates. This matches the existing entitySnapshot semantics (snapshot at step start).

## State-sync coverage
- `serializeState()` entity map: add `agility: e.agility ?? BASE_AGILITY[e.type] ?? 1`. The default fallback guards against old saves restored before migration.
- `deserializeState()` entity restoration: `Object.assign` already copies `agility` from the snapshot. Add an explicit back-compat line — `if (e.agility === undefined) e.agility = BASE_AGILITY[e.type] ?? 1;` — so pre-002 saves resume without `NaN` sort keys.
- `snapshotEntities()` in `server/resolver.js`: add `agility: e.agility` so replay/animation payloads carry the stat. (This is within the resolver file, already in the allowlist.)

No changes required to `src/planner.js` / `snapEntity` for correctness — sort runs on the live entity, not the snap — but adding `agility` there would be a cheap improvement. Leaving it out of this task to stay within the file allowlist.

## Test strategy

### `tests/resolver.test.js`
1. **Ordering within a step** — construct a minimal state with two hero units at different Agility values both queuing a MOVE this step; assert the higher-Agility unit's `ACTION_OK` event precedes the lower one in `step.playerEvents[0].events` (or `heroEvents` for the legacy path).
2. **Cross-faction interleave** — hero Agility=6, witch Agility=8; both queue BATTLE_UNIT against each other on turn 1. Witch must strike first; if she kills the hero, the hero's queued battle becomes a `skip` (entity dead) in the same step.
3. **Tie-break** — two units with identical Agility; assert the lower numeric id acts first. Include `e2` vs `e10` to lock numeric (not lexicographic) sort.
4. **Multi-step stability** — three units with distinct Agility values each queuing two MOVE actions; assert the same ordering applies on step 0 and step 1 (i.e. Agility is re-read each step, not cached).
5. **Dead actor** — queue an action from a unit that dies in an earlier step; confirm it drops out cleanly (skip event or no-op) without throwing inside the sort.

### `tests/state-sync.test.js`
1. Build a state with several entity types, mutate one entity's `agility` to a non-default value (e.g. 9), round-trip through `serializeState` → `deserializeState`, assert every entity's `agility` survives and the mutated entity still reads 9.
2. Construct a snapshot object lacking the `agility` field on entities (simulating a pre-002 save), deserialize, and assert `agility` populates from `BASE_AGILITY[type]` with no `undefined`.

### Balance check (manual, pre-merge)
`node scripts/headless.js 500 standard` and compare win rates / kill-win % / mean rounds against the 2026-04-23 baseline (Hero 55.2% / Witch 44.6%). Agility should not meaningfully swing these — both sides get it, the higher-Agility witch minion matches hero, and zombies/iron golems are already the witch's slower assets. If the shift exceeds ±5pp on either faction, retune the per-type defaults (most likely lever: lower MINION from 6 to 5 or raise ZOMBIE from 2 to 3).

## Risks
- **Determinism drift online vs offline.** Both orchestration layers share `server/resolver.js`, so sort logic is identical; the only risk is divergent entity state at step start. Serializing Agility closes that gap. Regression test: 2v2 headless (`--players 2`) passes without nondeterminism warnings.
- **Guard-strike timing.** `_checkGuardStrikes` runs inside `drainOneStep` after the actor resolves. Reordering callers doesn't change each caller's internal sequence, but a faster attacker now triggers guard strikes before a slower attacker's action runs — which is the intended behavior, not a bug. Documented in the test for cross-faction interleave.
- **Scatter cascade.** When a leader dies mid-step (`_handleLeaderDeath`), subsequent same-step candidates still execute in their pre-sorted order. Their actor lookups may now fail (scattered → removed entity), falling through to the existing skip path. Confirmed safe by test (5) above.
- **Pre-002 saves.** Covered by the `agility === undefined` back-compat hydrate in `deserializeState`.
- **Per-type default tuning.** Initial numbers are a judgement call; the balance check (Step 6) is the real validator. Plan leaves headroom to retune without touching resolver or state-sync again.
